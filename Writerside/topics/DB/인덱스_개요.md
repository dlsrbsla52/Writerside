# 인덱스 개요

아래는 인덱스가 어떻게 동작하는지, 언제 유리하게 사용되고 언제 문제가 될 수 있는지를 이해하는 데 도움이 되는 예제들과 함께 자세한 설명입니다.

---

## 인덱스란 무엇인가?

- **인덱스(Index)** 는 테이블의 데이터를 빠르게 검색하기 위해 사용하는 별도의 자료구조입니다.
- **장점:**
    - **빠른 검색:** WHERE 절이나 JOIN, ORDER BY 등에 사용되는 컬럼에 대해 빠른 접근을 가능하게 합니다.
    - **정렬 최적화:** 이미 정렬된 순서대로 저장되므로 정렬 비용을 줄일 수 있습니다.
- **단점:**
    - **추가 저장공간:** 테이블 외에 별도의 공간이 필요합니다.
    - **쓰기 비용:** INSERT, UPDATE, DELETE 시 인덱스도 함께 수정되어야 하므로 비용이 증가합니다.

---

## 테이블 구조

우리가 다룰 테이블은 다음과 같습니다.

```sql
create table article
(
    article_id  bigint        not null,  -- 기본키, 고유 인덱스가 자동 생성됨
    title       varchar(100)  not null,
    content     varchar(3000) not null,
    board_id    bigint        not null,
    writer_id   bigint        not null,
    created_at  datetime      not null,
    modified_at datetime      not null,
    primary key (article_id)
);
```

**참고:**

- `article_id`는 기본키이므로 이미 고유 인덱스가 생성되어 있어, `WHERE article_id = ?` 같은 조건에는 매우 효율적입니다.

---

## 다양한 검색 및 정렬 시나리오와 인덱스 설계

### 예제 **기본 키 검색**

**쿼리:**

```sql
-- 특정 article_id로 검색
SELECT * FROM article
WHERE article_id = 123;
```

**동작 원리:**

- 이미 `article_id`에 대해 기본키 인덱스가 생성되어 있으므로, DB는 **Index Unique Scan** (또는 **Primary Key Lookup**) 을 사용하여 빠르게 해당 로우를 찾습니다.

**실행 계획 예시:**

```
Index Scan using article_pkey on article  (cost=... rows=1 ...)
```

---

### **board_id 조건과 created_at 정렬**

**쿼리:**

```sql
-- 특정 게시판(board_id)의 글을 최근순(created_at DESC)으로 조회 후 페이징
SELECT *
FROM article
WHERE board_id = 1
ORDER BY created_at DESC
LIMIT 30 OFFSET 90;
```

**문제점:**

- 현재 인덱스(예: `idx_board_id_article_id` 등)가 있다 하더라도 **created_at** 컬럼이 인덱스에 포함되어 있지 않으면,
    1. **board_id**에 해당하는 로우들은 빠르게 필터링할 수 있지만,
    2. 그 후 **created_at** 기준으로 정렬을 위해 추가 정렬 작업(sort)이 필요해집니다.

**개선 방안:**

- **조건**과 **정렬** 모두를 만족하는 **복합 인덱스**를 생성합니다.

```sql
-- board_id로 필터링하고, created_at DESC 정렬까지 고려한 인덱스 생성
CREATE INDEX idx_board_created ON article(board_id, created_at DESC);
```

**동작 원리:**

- **WHERE board_id = 1** 조건에 따라 인덱스의 첫 번째 컬럼을 사용해 해당 로우를 빠르게 필터링합니다.
- 인덱스 내부에서 **created_at**이 내림차순으로 정렬되어 있으므로, 정렬 단계 없이 바로 LIMIT, OFFSET 처리할 수 있습니다.

**실행 계획 예시:**

```
Index Scan using idx_board_created on article  (cost=... rows=... ...)
```

### **writer_id와 날짜 범위 조건**

**쿼리:**

```sql
-- 특정 작성자(writer_id)의 게시글을 최근 1년간 조회, 최신순 정렬
SELECT *
FROM article
WHERE writer_id = 100
  AND created_at >= '2024-02-01'
  AND created_at <  '2025-02-01'
ORDER BY created_at DESC;
```

**개선 방안:**

- **복합 인덱스**를 활용하면, 두 조건(writer_id, created_at) 모두를 효과적으로 사용할 수 있습니다.

```sql
-- writer_id와 created_at DESC를 고려한 인덱스 생성
CREATE INDEX idx_writer_created ON article(writer_id, created_at DESC);
```

**동작 원리:**

- 인덱스는 먼저 `writer_id`로 필터링한 후, 날짜 범위 (`created_at`)에 해당하는 로우들만 인덱스 상에서 선택합니다.
- 인덱스 내의 **created_at** 순서가 이미 내림차순이므로, 정렬 비용 없이 결과를 반환합니다.

**실행 계획 예시:**

```
Index Scan using idx_writer_created on article  (cost=... rows=... ...)
```

### **부분 검색 및 다중 조건**

경우에 따라 하나의 인덱스가 모든 쿼리 패턴을 최적화하지 못할 수도 있습니다.  
예를 들어, 만약 다음과 같이 제목(title)이나 내용(content)에 대해 LIKE 검색을 수행한다면:

```sql
-- 제목에 특정 단어가 포함된 게시글 검색
SELECT *
FROM article
WHERE title LIKE '%검색어%';
```

**고려 사항:**

- 일반적인 B-Tree 인덱스는 접두사 검색(prefix search)에는 유용하지만, `%검색어%`와 같이 중간 또는 뒤쪽에 와일드카드가 있으면 사용할 수 없습니다.
- 이런 경우 **Full Text Search** 또는 **특수 인덱스** (예: PostgreSQL의 GIN 인덱스)를 고려해야 합니다.

예를 들어, PostgreSQL에서는 다음과 같이 사용할 수 있습니다.

```sql
-- PostgreSQL 예시: tsvector를 사용한 Full Text Index 생성
ALTER TABLE article
ADD COLUMN tsv tsvector;

-- tsv 컬럼 업데이트 (트리거 등을 사용하여 자동 갱신 가능)
UPDATE article
SET tsv = to_tsvector('korean', title || ' ' || content);

-- GIN 인덱스 생성
CREATE INDEX idx_article_tsv ON article USING gin(tsv);

-- Full Text Search 쿼리 예시
SELECT *
FROM article
WHERE tsv @@ plainto_tsquery('korean', '검색어');
```

## 인덱스 선택과 실행 계획에 관한 팁

- **실행 계획 확인:**
    
    - `EXPLAIN` 또는 `EXPLAIN ANALYZE` 명령어를 사용해서 쿼리 실행 계획을 확인합니다.
    - 인덱스 스캔(Index Scan) 또는 인덱스 범위 스캔(Index Range Scan)이 사용되는지, 정렬(Sort) 단계가 발생하는지 확인합니다.
- **인덱스 설계 원칙:**
    
    1. **쿼리의 WHERE 절, JOIN 조건, ORDER BY 절 분석:**
        - 가장 자주 사용되는 조건이나 정렬 순서를 인덱스의 컬럼 순서에 반영합니다.
    2. **선택도(Selectivity) 고려:**
        - 값의 다양성이 높은 컬럼을 앞쪽에 배치하면 효율적입니다.
    3. **Covering Index:**
        - 쿼리에서 SELECT하는 컬럼들이 인덱스에 모두 포함되면, 테이블 접근(Heap Fetch)을 피할 수 있습니다.
            
        - 예를 들어, 만약 `SELECT article_id, title, created_at FROM article ...`처럼 자주 사용된다면, 아래와 같이 인덱스를 구성할 수 있습니다.
            
            ```sql
            CREATE INDEX idx_board_created_covering ON article(board_id, created_at DESC) INCLUDE (article_id, title);
            ```
            
            _주의: INCLUDE 구문은 일부 DBMS(Microsoft SQL Server, PostgreSQL 11 이상 등)에서 지원합니다._
            
- **불필요한 인덱스 주의:**
    
    - 너무 많은 인덱스는 쓰기 성능에 영향을 주므로, 실제 사용되는 쿼리 패턴을 분석하여 꼭 필요한 인덱스만 생성합니다.

---

## 최종 정리

1. **쿼리 분석:**
    
    - 먼저 실행할 쿼리의 WHERE, JOIN, ORDER BY 조건을 분석합니다.
    - 예를 들어, `WHERE board_id = 1 ORDER BY created_at DESC`라면, **board_id**와 **created_at**가 주요 컬럼입니다.
2. **적절한 인덱스 설계:**
    
    - 조건과 정렬 컬럼을 모두 포함하는 **복합 인덱스**를 생성합니다.
    - 예:
        
        ```sql
        CREATE INDEX idx_board_created ON article(board_id, created_at DESC);
        ```
        
3. **실행 계획 확인:**
    
    - `EXPLAIN`을 통해 인덱스 스캔이 사용되는지, 추가 정렬 작업이 없는지 확인합니다.
    - 인덱스가 제대로 사용되면 **Index Scan** 혹은 **Range Scan**이 보이며, 불필요한 Sort 연산이 없어야 합니다.
4. **특수 케이스:**
    
    - LIKE 검색, FULL TEXT 검색 등 특수 검색은 별도의 인덱스(GIN, GiST 등)를 고려합니다.
    - 다중 조건의 경우, 어떤 조건의 선택도가 높은지에 따라 인덱스 컬럼 순서를 결정합니다.

---

이와 같이, **쿼리 패턴에 맞게 인덱스를 설계**하면 실행 계획에서 인덱스 스캔이 효과적으로 사용되어 검색 속도를 대폭 향상시킬 수 있습니다. 반대로 인덱스가 쿼리 조건과 맞지 않으면 오히려 불필요한 정렬이나 테이블 접근이 발생해 성능 저하를 일으킬 수 있으므로, 쿼리와 데이터 특성을 꼼꼼하게 분석하는 것이 중요합니다.
