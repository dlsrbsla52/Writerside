# 커버링 인덱스

DB 옵티마이저와 커버링 인덱스에 대해 깊게 이해하는 것은 데이터베이스 성능 튜닝의 핵심입니다. 아래에 단계별로 자세하게 설명해볼게요.

---

## 1. DB 옵티마이저의 작동 과정

### 1.1. 쿼리 파싱과 분석

- **파싱(Parsing):**  
    SQL 쿼리가 데이터베이스에 도착하면, 우선 구문 분석(parser)이 실행되어 쿼리를 구문 트리(AST)로 변환합니다.
    
    > 예: `SELECT * FROM article WHERE board_id = 1`  
    > → AST로 변환되어, 테이블 이름, 컬럼, 조건 등이 분리됩니다.
    
- **검증 및 바인딩(Binding):**  
    분석된 쿼리가 실제 스키마와 맞는지 확인합니다. 테이블과 컬럼이 존재하는지, 데이터 타입이 올바른지 검증합니다.
    

### 1.2. 쿼리 재작성(Query Rewrite)

- 옵티마이저는 내부 규칙(rule)을 적용해 쿼리를 더 효율적인 형태로 재작성합니다.  
    예를 들어, 뷰(view)를 확장하거나 서브쿼리를 단순화할 수 있습니다.

### 1.3. 실행 계획(Execution Plan) 생성

- **후보 실행 계획 탐색:**  
    옵티마이저는 다양한 “액세스 경로(Access Path)”를 고려합니다. 예를 들어,
    
    - **전체 테이블 스캔(Sequential Scan):** 테이블의 모든 로우를 읽음.
    - **인덱스 스캔(Index Scan):** 조건에 맞는 로우만 인덱스를 통해 찾음.
    - **인덱스 전용 스캔(Index Only Scan):** 인덱스에 필요한 모든 컬럼이 포함되어 있을 때, 테이블(Heap) 접근 없이 인덱스만 사용.
- **비용 추정(Cost Estimation):**  
    각 실행 계획에 대해 예상 비용(I/O, CPU, 메모리 사용량 등)을 산출합니다.  
    이때 테이블 통계(로우 수, 데이터 분포 등)가 사용됩니다.
    
- **최적 실행 계획 선택:**  
    비용이 가장 낮다고 판단되는 계획을 최종 선택하여 실행합니다.
    

### 1.4. 실행 단계

- 선택된 실행 계획에 따라 데이터가 실제로 검색됩니다.  
    예를 들어, 인덱스 스캔을 선택한 경우, B-Tree와 같은 자료구조를 따라 조건에 맞는 인덱스 엔트리를 찾고, 필요한 경우 해당 로우의 데이터를 테이블에서 읽어옵니다.

## 2. 커버링 인덱스(Covering Index)란?

### 2.1. 정의와 기본 개념

- **커버링 인덱스:**  
    쿼리에서 필요한 모든 컬럼을 인덱스 자체에 포함시켜, 인덱스만으로 쿼리 결과를 “커버(cover)”할 수 있는 인덱스입니다.
    
- **Index Only Scan:**  
    커버링 인덱스가 존재하면, 옵티마이저는 인덱스 전용 스캔을 사용하여 테이블(Heap)에 접근하지 않고 인덱스만으로 데이터를 반환할 수 있습니다.
    

### 2.2. 예제

예를 들어, 아래 쿼리를 고려해봅시다:

```sql
-- 자주 사용되는 쿼리: board_id 조건, created_at 정렬, 일부 컬럼 선택
SELECT article_id, title, created_at
FROM article
WHERE board_id = 1
ORDER BY created_at DESC
LIMIT 30;
```

이때, 만약 인덱스에 **board_id**와 **created_at**만 있다면, 인덱스 스캔 후 테이블 접근(Heap Fetch)이 필요합니다.  
하지만 커버링 인덱스를 사용하면:

```sql
CREATE INDEX idx_board_created_covering
ON article(board_id, created_at DESC)
INCLUDE (article_id, title);
```

- 인덱스 내부에 **board_id**, **created_at** (검색 및 정렬용)와 **article_id**, **title** (SELECT 절에서 사용되는 컬럼)이 모두 포함됩니다.
- 실행 계획에서는 **Index Only Scan**이 사용되어, 테이블을 직접 조회하지 않고 인덱스에서 모든 데이터를 바로 반환할 수 있습니다.

## 3. 커버링 인덱스 사용 시 장점과 주의사항

### 3.1. 장점

- **향상된 성능 (빠른 I/O):**
    - 인덱스만으로 쿼리를 해결할 수 있으므로, 디스크 I/O가 크게 줄어듭니다.
    - 특히 테이블이 크거나 자주 조회되는 경우 효과적입니다.
- **낮은 CPU 비용:**
    - 추가적인 테이블 접근 없이 인덱스에서 바로 결과를 추출하므로 CPU 사용량이 줄어듭니다.
- **높은 캐시 효율성:**
    - 인덱스 크기가 테이블보다 작을 가능성이 높아, 메모리 캐시에 더 잘 올라가서 조회 속도가 개선됩니다.

### 3.2. 주의사항

- **인덱스 크기 증가:**
    
    - SELECT 절에 자주 사용되는 컬럼들을 INCLUDE하거나 인덱스 키에 추가하면, 인덱스 자체의 크기가 커집니다.
    - 큰 인덱스는 메모리와 저장 공간을 더 많이 사용하게 됩니다.
- **쓰기 작업 비용 증가:**
    
    - INSERT, UPDATE, DELETE 작업 시, 인덱스도 함께 업데이트되어야 하므로, 커버링 인덱스가 많으면 쓰기 성능에 부정적인 영향을 줄 수 있습니다.
- **적용 대상 쿼리의 특수성:**
    
    - 커버링 인덱스는 특정 쿼리 패턴에 최적화된 경우에만 유리합니다.
    - 모든 쿼리에 대해 항상 성능 향상을 보장하지는 않으므로, 사용 빈도와 쿼리 특성을 고려해야 합니다.
- **통계와 옵티마이저 선택:**
    
    - DB의 통계 정보가 부정확하면, 옵티마이저가 커버링 인덱스의 장점을 제대로 활용하지 못할 수 있습니다.
    - 주기적인 통계 업데이트와 모니터링이 필요합니다.

---

## 4. 결론

- **DB 옵티마이저는**  
    쿼리를 파싱, 재작성, 비용 산출 단계를 거쳐 여러 실행 계획 중 가장 효율적인 계획을 선택합니다.  
    이 과정에서 인덱스의 존재와 구조가 중요한 역할을 하며, 올바른 인덱스 설계는 빠른 데이터 접근을 가능하게 합니다.
    
- **커버링 인덱스는**  
    쿼리에서 필요한 모든 컬럼을 인덱스 내부에 포함시켜, 테이블에 접근하지 않고 인덱스만으로 결과를 반환할 수 있는 기법입니다.  
    이는 I/O 비용과 CPU 부하를 줄여 성능을 개선하지만, 인덱스 크기와 쓰기 작업 비용 증가 같은 단점을 동반합니다.
    

커버링 인덱스를 설계할 때는, 자주 사용되는 조회 패턴과 SELECT 절의 컬럼들을 꼼꼼히 분석하여, **"어떤 쿼리에서 인덱스만으로 모든 데이터를 커버할 수 있을지"**를 판단하고, 실제 실행 계획(EXPLAIN)을 확인하며 튜닝하는 것이 좋습니다.
